# Team conventions

Every agent and skill follows these rules. The goal: **the user sees finished work, not the team's paperwork.** One task produces one clear deliverable, one short reply, and one link that opens it in the Marketing Hub.

## 1. Read before you work

1. **The brand brief** — `marketing/brand-brief.md` (in a claude.ai chat with no folder, the Project's knowledge files). Product facts, audience, positioning, voice, terminology, CTAs, red lines.
2. **The strategy for your area** — `marketing/strategy/`. `marketing-strategy.md` applies to everyone; then `seo.md`, `content.md`, `social.md`, `paid.md` or `email.md`. If your work would break a strategy rule, say so instead of quietly deviating.
3. **The brand kit** for anything visual — `marketing/design/brand-kit.md`.
4. **The brief you were handed**, if any.
5. **The work index** — `marketing/index.md` lists everything the team has made (generated by the Hub). Check it to avoid duplicates and to find things to link to or reuse.

No brand brief? For a quick task, go ahead and state your assumptions in the deliverable's notes; for larger work, offer `brand-setup` first. Never hard-code brand facts into skills or agents.

## 2. Workspace layout

Flat, one folder per area, short readable file names. **No dates in file names** (the date lives in the file's header) and no folders-per-item unless the item has several files.

```
marketing/
├── hub.html            ← the Marketing Hub: open this
├── index.md            ← list of all work (generated; don't edit)
├── brand-brief.md
├── artifacts.md        ← links to work that lives in Claude (designs, design system, videos)
├── strategy/           marketing-strategy.md · seo.md · content.md · social.md · paid.md
├── web/                blog articles, new pages, page refreshes
├── social/             posts, repurpose sets, weekly calendars
├── video/              video plans and briefs (a folder per video only when it has assets)
├── design/             brand-kit.md · assets/ · graphics/<name>/
├── ads/                campaign plans, ad copy, performance reviews
├── sales/              battlecards, one-pagers, talk tracks
├── launches/<name>/    launch kit (plan.md, messaging.md)
├── campaigns/<name>/   campaign plan
├── research/           audits, keyword research, gap analyses, GTM analyses, reviews
├── queue/              briefs waiting for an agent (the work queue)
├── site/  ai-visibility/  dashboards/      ← team's working data
```

**File names:** 2–5 words, lowercase, hyphens, describing the thing: `web/homepage-refresh.md`, `social/week-46-calendar.md`, `research/seo-audit-november.md`, `sales/battlecard-competitor-a.md`. If the name exists, add a word that distinguishes it rather than a date.

## 3. One task, one deliverable file

Every deliverable is **one Markdown file** with this header, then the content, then a short notes section:

```
---
title: Homepage refresh
type: page-refresh      # blog · page · page-refresh · social · calendar · video · graphic · ad · ad-review · sales · launch · campaign · research · strategy · review
agent: web-content-agent
status: draft           # draft · needs-review · approved · published
date: 2026-11-06
summary: New homepage copy that leads with the fractional offer.
needs_you:
  - Pick one of the two hero headlines
  - Add a screenshot of the case-study page
---

# Homepage refresh

…the deliverable itself, ready to use…

## Notes for you
Short: what to check before publishing ([VERIFY] items), where to paste it, internal links to add elsewhere. No process narration.
```

- The **first screen** of the file is the usable thing (the copy, the posts, the plan's summary) — not methodology.
- `needs_you` lists only real actions for the user (approve, choose, supply, verify). Empty list if none. These become the Hub's inbox.
- Supporting material goes **inside the same file** under `## Notes for you` or an appendix. Create a second file only when it is genuinely separate (research notes for a large analysis, a launch kit's messaging doc, graphics).
- Keep the status current: set `approved` / `published` when the user says so.

## 4. Briefs: the work queue, used sparingly

A brief is a note from one agent to another about work **for later**. It is not paperwork for every task.

- **Never create a brief for the user's own request** — the request is the brief. Just do the work.
- **Don't create follow-up briefs on your own.** Suggest follow-ups in your reply ("Want LinkedIn posts about it?"). Create briefs only when the user says yes, or when the user's request itself needs several agents (e.g., a launch).
- At most **3 briefs** per task unless the user asks for more.
- Briefs live in `marketing/queue/`, named for the work (`linkedin-posts-homepage.md`), using `${CLAUDE_PLUGIN_ROOT}/templates/brief.md` — short. Status: `ready` → `in-progress` → `done` (with `output:` set to the deliverable's path).
- Subagents can't call each other; the team lead relays queue items.

## 5. Replying to the user: the done message

Finish **every** task with this, and nothing else:

```
Done: <Title> (<area>)
→ <one link that opens it — the Hub item, or the Claude design/doc>

Needs you:
1. <action>            (max 3; omit the section if none)

Next? <one suggested follow-up as a yes/no question>   (optional)
```

- **No file paths, folder trees, lists of files touched, process steps or tool narration.** The user can ask for details.
- Explain only what the user must know to act (a risk, a blocking question).
- The link: if the Hub is published as an artifact, link to it with `#<item-id>` (the item id is the file path without `marketing/` and `.md`, slashes as `--`, e.g. `#web--homepage-refresh`); otherwise link the deliverable file itself.

## 6. Keep the Hub current (silently)

At the end of a task, rebuild the Hub and index — don't mention it in the reply:

```
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/hub.py --workspace marketing
```

If the session can publish artifacts and the Hub has been published before (link in `marketing/artifacts.md`), republish it to the same artifact. In a git workspace: `git pull` before starting; commit (`<agent>: <title>`) and push at the end.

## 7. Work that lives in Claude (artifacts)

Design canvases, the design system, Motion videos and published dashboards live in Claude. Record each in `marketing/artifacts.md` (`| Date | Type | Title | Link | Related work | Agent |`) and put the link in the related deliverable's header as `link:`. Revise existing artifacts instead of creating duplicates. Where artifact tools aren't available, use the file-based fallback the skill describes.

## 8. Depth and evidence

- Research follows `${CLAUDE_PLUGIN_ROOT}/templates/research-standards.md`; strategic work follows `${CLAUDE_PLUGIN_ROOT}/templates/analysis-standards.md`.
- Never invent statistics, customer names, quotes, awards, prices or feature claims. Product claims come from the brand brief or the user's own pages; external facts need a source link. Mark anything unverified `[VERIFY]` and list it in the notes.
- Be fair to competitors; compare on facts.
- If the session blocks you from writing files, return the complete deliverable (header included) in your final message so the team lead can save it.

## 9. Visuals and dashboards

Reports with numbers also get a visual dashboard per `${CLAUDE_PLUGIN_ROOT}/templates/dashboards.md`, saved in `marketing/dashboards/` and linked from the deliverable's header (`dashboard:`). Produce Word, PowerPoint or PDF only when asked. Work autonomously: make sensible choices and state them in the notes; ask only when a missing input would make the result wrong.
